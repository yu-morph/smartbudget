# API 명세와 테스트 화면

## 기본 구성

로컬 기본 주소는 `http://127.0.0.1:8000`입니다. Azure 배포 후에는 App Service 개요에 표시되는 기본 도메인을 사용합니다. 아래 모든 경로는 기본 주소 뒤에 붙입니다.

| 메서드 | 경로 | 응답 |
| --- | --- | --- |
| GET | `/` | 테스트용 HTML 화면 |
| GET | `/transactions` | 필터링된 거래 JSON |
| GET | `/docs` | Swagger UI API 문서 |
| GET | `/openapi.json` | OpenAPI 명세 |

날짜, 기간, 설명, 카테고리, 유형이라는 다섯 가지 조회 목적을 **하나의 조회 API와 선택적 쿼리 파라미터**로 처리합니다. 목적별 API를 따로 호출할 필요 없이 조건을 조합합니다. 인증 헤더나 요청 본문은 필요하지 않습니다.

## 쿼리 파라미터

| 이름 | 형식 | 의미 |
| --- | --- | --- |
| `date` | `YYYY-MM-DD` | 정확히 하루 조회 |
| `startDate` | `YYYY-MM-DD` | 기간 시작일, 해당 날짜 포함 |
| `endDate` | `YYYY-MM-DD` | 기간 종료일, 해당 날짜 포함 |
| `description` | 문자열 | 설명의 대소문자 구분 없는 부분 일치 |
| `category` | 아래 표의 영문 값 | 카테고리 정확히 일치 |
| `type` | `INCOME` 또는 `EXPENSE` | 수입 또는 지출 |

모든 파라미터는 생략할 수 있습니다. 조건을 여러 개 보내면 모두 만족하는 거래만 반환하는 AND 검색입니다. 날짜 조건이 없으면 미래 날짜를 포함해 전체 데이터 기간을 대상으로 합니다.

### 날짜 규칙

- `date`는 `startDate`, `endDate` 중 어느 것과도 함께 사용할 수 없습니다.
- 시작일과 종료일이 같으면 하루를 조회합니다.
- `startDate`만 보내면 시작일부터 **서버의 오늘**까지 조회합니다.
- `endDate`만 보내면 데이터의 최초 날짜인 `2024-01-02`부터 조회합니다.
- 시작일이 종료일보다 늦으면 `400`입니다. 시작일만 보냈는데 서버의 오늘보다 미래여도 동일합니다.
- `20260101`, `2026-1-1`, 날짜·시간 문자열, 존재하지 않는 날짜는 허용하지 않습니다.
- 데이터가 없는 날짜는 정상 요청이면 빈 결과를 반환합니다. 다만 종료일만 보내 최초 데이터 날짜보다 앞선 경우에는 계산된 시작일이 종료일보다 늦어져 `400`입니다.

`서버의 오늘`은 Python `date.today()` 기준입니다. 한국 시간대를 명시적으로 설정하지 않았으므로 배포 환경의 날짜와 사용자 기기의 날짜가 다를 수 있습니다. 재현 가능한 과제 시연에는 양쪽 날짜를 명시하세요. 데이터는 고정이지만 시작일만 쓰는 조회의 결과는 날짜가 지나면서 달라질 수 있습니다.

### 카테고리와 유형

| 유형 | category | 화면 표시 |
| --- | --- | --- |
| EXPENSE | `food` | 식비 |
| EXPENSE | `transport` | 교통 |
| EXPENSE | `shopping` | 쇼핑 |
| EXPENSE | `housing_utilities` | 주거·공과금 |
| EXPENSE | `health` | 건강 |
| EXPENSE | `leisure` | 여가 |
| EXPENSE | `education` | 교육 |
| EXPENSE | `other_expense` | 기타 지출 |
| INCOME | `salary` | 급여 |
| INCOME | `side_income` | 부업 수입 |
| INCOME | `investment_income` | 투자 수입 |
| INCOME | `other_income` | 기타 수입 |

카테고리와 유형은 대소문자를 구분합니다. `food&type=INCOME`처럼 각각 유효하지만 서로 맞지 않는 조합은 오류 대신 0건을 반환합니다. 빈 `description`은 필터를 적용하지 않지만, 공백은 자동으로 제거하지 않습니다. 빈 날짜·카테고리·유형은 보내지 말고 파라미터 자체를 생략하세요.

## 요청 예시

```bash
# 전체 조회
curl 'http://127.0.0.1:8000/transactions'

# 특정 날짜
curl 'http://127.0.0.1:8000/transactions?date=2026-12-31'

# 기간 + 카테고리 + 유형
curl 'http://127.0.0.1:8000/transactions?startDate=2026-01-01&endDate=2026-12-31&category=food&type=EXPENSE'

# 한글 검색어는 URL 인코딩
curl --get 'http://127.0.0.1:8000/transactions' --data-urlencode 'description=카페'

# 수입만 조회
curl 'http://127.0.0.1:8000/transactions?type=INCOME'
```

## 응답 계약

날짜 내림차순, 같은 날짜에서는 거래 ID 내림차순으로 정렬합니다. `count`는 현재 조건에 맞는 전체 건수이고, 페이지네이션 없이 해당 거래를 전부 반환합니다.

```json
{
  "count": 1,
  "transactions": [
    {
      "transactionId": "txn-000001",
      "date": "2024-01-02",
      "description": "한빛식당",
      "category": "food",
      "amount": 59100,
      "type": "EXPENSE"
    }
  ]
}
```

위 예시는 응답 구조를 설명하기 위한 것입니다. 요청별 실제 결과는 API에서 확인합니다.

| 필드 | JSON 타입 | 설명 |
| --- | --- | --- |
| `transactionId` | string | 원본 행 순서를 기반으로 생성한 고유 ID |
| `date` | string | 시간·시간대 없는 거래 날짜 |
| `description` | string | 한국어 가맹점명 또는 입금 설명 |
| `category` | string | 고정된 12개 카테고리 중 하나 |
| `amount` | integer | 원화 금액, 양수, 100원 단위 |
| `type` | string | `INCOME` 또는 `EXPENSE` |

지출도 API 금액은 양수입니다. 차액을 계산할 때 유형을 기준으로 수입을 더하고 지출을 빼야 합니다. 통화는 KRW로 고정이며 별도 통화 필드는 없습니다.

### 빈 결과와 오류

검색 결과가 없으면 `200 OK`입니다.

```json
{"count": 0, "transactions": []}
```

잘못된 날짜, 카테고리, 유형 또는 상충하는 날짜 조건은 `400 Bad Request`입니다. 기간 규칙 오류는 다음처럼 문자열 `detail`을 반환합니다.

```json
{"detail": "시작일은 종료일보다 늦을 수 없습니다"}
```

날짜 형식·열거형 검증 오류는 `detail`이 오류 객체 배열입니다. 클라이언트는 모든 오류가 문자열이라고 가정하면 안 됩니다. 상세 검증 객체의 필드는 FastAPI/Pydantic 버전에 따라 달라질 수 있습니다.

## 테스트 화면 사용법

1. 서버 실행 후 `/`에 접속합니다. 최초에는 전체 거래를 조회합니다.
2. 날짜 조회 방식에서 전체 기간, 특정 날짜, 기간 선택 중 하나를 선택합니다.
3. 달력으로 날짜를 지정하고 카테고리·거래 유형 드롭다운과 설명 검색을 필요에 따라 입력합니다.
4. **거래 조회**를 누릅니다. 필터를 바꾸기만 해서는 기존 결과가 갱신되지 않습니다.
5. 결과 건수, 수입 합계, 지출 합계와 거래 표를 확인합니다. 합계는 조회된 결과에 대해서만 브라우저에서 계산합니다.
6. **실제 API 요청 보기**를 펼쳐 요청 경로를 확인하거나 링크를 열어 JSON을 봅니다.
7. **초기화**를 누르면 입력 조건을 비우고 전체 거래를 다시 조회합니다.

기간 선택에서 시작일·종료일을 모두 비우면 날짜 필터 없이 조회합니다. 달력 모양은 브라우저·운영체제에 따라 다릅니다. HTML 파일을 직접 열지 말고 반드시 서버 주소로 접속하세요.

## 다른 앱에서 호출할 때

현재 테스트 화면은 API와 같은 출처에서 상대 경로로 호출하므로 별도 CORS 설정이 필요하지 않습니다. 다른 도메인이나 포트의 브라우저 프론트엔드에서 호출하려면 허용할 출처를 정한 뒤 CORS 설정을 추가해야 합니다. 현재는 해당 설정이 없습니다. 서버 간 호출과 curl에는 브라우저의 CORS 제한이 적용되지 않습니다.

API는 공개 목업 조회용입니다. 실제 금융정보나 개인 데이터를 추가해서 공개 배포하면 안 됩니다.
